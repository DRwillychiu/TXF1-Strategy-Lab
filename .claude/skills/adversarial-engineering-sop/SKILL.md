# Adversarial Engineering SOP — 六階段對抗式工程流程

## 觸發場景
- 策略大版本升級（V2.x → V3.x）
- 跨平台遷移（MC9 ↔ MC12、PowerLanguage → Python）
- 多檔案結構性重構
- 任何影響 ≥ 3 個檔案的改動
- 用戶明確要求「走對抗式流程」或「adversarial SOP」

## 核心哲學

```
一個工程師，在循環之外。
閱讀產出、編輯循環、把關每個階段。
```

| 角色 | 說明 |
|------|------|
| 執行 (藍) | 產出程式碼 / 翻譯 / 修復 |
| 審查 (紅) | 預設立場＝有 BUG，攻擊每個產出 |
| 共享文檔 (黃) | 規則比程式碼活得更久，文檔是跨階段的唯一真相源 |

**鐵律**：執行者不審查自己的產出。審查者預設不通過。

---

## 第 0 步：自我驗證假設（每階段前置）

> **假設整套有 BUG，該如何解決？**

在每個階段啟動前，必須回答三個問題：

| # | 問題 | 產出 |
|---|------|------|
| Q1 | 如果這個階段的產出全部是錯的，最壞後果是什麼？ | 最壞情境描述 |
| Q2 | 什麼證據能證明產出是錯的？（反證清單） | 具體可檢驗的反證條件 |
| Q3 | 如果發現是錯的，回滾路徑是什麼？ | 回滾指令 / git ref / 備份位置 |

**只有三個問題都有明確答案，才進入該階段。**

### 階段間 Bug 傳播檢查

每完成一個階段，檢查：

```
本階段產出的假設 → 是否被下一階段繼承？
如果本階段的某個決策是錯的 → 下游哪些產出會連帶出錯？
連帶出錯的範圍 → 是否有獨立驗證手段（不依賴本階段的正確性）？
```

---

## 第 1 步：制定規則手冊

**產出**：可信的規則 + 依賴圖

| 任務 | 角色 | 說明 |
|------|------|------|
| 規則手冊撰寫 | 執行 | 每個決策寫一條規則，含 WHY + 適用範圍 + 邊界案例 |
| 依賴圖生成 | 執行 | 排列工作順序（哪些先做、哪些可平行） |
| 差異清單 | 執行 | 追蹤所有控制流變更點 |
| 規則審計 | 審查 | 每類錯誤至少一條規則覆蓋 |
| 懷疑論審查 ×2 | 審查 | 攻擊每條規則：「什麼情境下這條規則會導致錯誤決策？」 |
| 聯合審計 | 審查 | 差異清單 vs 規則手冊，確認一致性（無遺漏、無矛盾） |

### 自我驗證
- Q1：規則手冊有遺漏 → 後續所有階段在盲區內犯錯且無人發現
- Q2：反證 = 找到一個真實案例不被任何規則覆蓋
- Q3：回滾 = 補充規則，重跑懷疑論審查

**Gate**：規則手冊 + 依賴圖 + 差異清單三份文件齊全，懷疑論審查無未解 issue → 通過

---

## 第 2 步：壓力測試規則

**產出**：加固後的規則

| 任務 | 角色 | 說明 |
|------|------|------|
| 雙重翻譯 ×2 | 執行 | 同一檔案，不同上下文各翻譯一次 |
| 差異檢查員 | 審查 | 兩份翻譯的差異 → 規則不夠精確的地方 → 修訂規則 |
| 試跑 | 執行 | 選 2-3 個代表性檔案做完整演練 |

### 自我驗證
- Q1：規則看似完整但在邊界案例失效 → 全量翻譯時重複犯同一類錯
- Q2：反證 = 試跑結果與規則預測不符
- Q3：回滾 = 修訂規則手冊，重新試跑

**Gate**：試跑結果與規則預測一致，差異檢查員無新發現 → 通過

---

## 第 3 步：全量執行

**隊列**：檔案列表（依賴圖順序）

| 任務 | 角色 | 說明 |
|------|------|------|
| 翻譯/執行 Agent | 執行 | 每個檔案一個 Agent，嚴格按規則手冊 |
| 審查 ×2 | 審查 | **預設立場：假設程式碼有錯**，逐行比對規則 |
| 修復 Agent | 執行 | 只應用已確認的修復（審查通過的） |

### 自我驗證
- Q1：Agent 系統性誤解某條規則 → 大量檔案同類錯誤
- Q2：反證 = 抽查 3 個檔案，若 ≥1 個有同類問題 → 系統性問題
- Q3：回滾 = git revert 到全量執行前，修訂規則，重跑

**Gate**：所有檔案通過雙重審查，抽查無系統性問題 → 通過

---

## 第 4 步：編譯 / 靜態驗證

**隊列**：編譯錯誤

| 任務 | 角色 | 說明 |
|------|------|------|
| 統一構建 ×1 | 執行 | 一次編譯全部，收集所有錯誤 |
| 平行修復 | 執行 | 修復者無編譯器存取權（防止 trial-and-error） |
| 仲裁審查 | 審查 | **預設不通過**，修復必須解釋 WHY 而非只是 WHAT |

### 自我驗證
- Q1：修復了症狀但沒修根因 → 運行時才炸
- Q2：反證 = 修復說明中缺少「根因分析」的修復項
- Q3：回滾 = 還原該修復，要求附帶根因分析重新提交

**Gate**：零編譯錯誤 + 所有修復含根因分析 → 通過

---

## 第 5 步：運行 / 冒煙測試

**隊列**：去重後的崩潰

| 任務 | 角色 | 說明 |
|------|------|------|
| 冒煙測試 | 執行 | 刻意暴露崩潰（走 edge case 路徑） |
| 按根因修復 | 執行 | 按根因分組（不是按症狀），一次修一類 |
| 審查 ×2 | 審查 | 驗證每個修復，確認未引入新問題 |

### 策略工程特化（TXF1）
- 冒煙測試必含：結算日進出場、假日平倉、夜盤跨日、極端波動停損
- 回測比對：修改前後 trade list 逐筆 diff，差異筆數必須可解釋

### 自我驗證
- Q1：修復 A 引入了 Bug B → 修復迴圈無限
- Q2：反證 = 修復後重跑冒煙測試，出現新崩潰
- Q3：回滾 = git revert 該修復，改用不同修復策略

**Gate**：冒煙測試全過 + 回測 diff 每筆差異都有解釋 → 通過

---

## 第 6 步：行為對齊

**隊列**：失敗的測試 → 合併

| 任務 | 角色 | 說明 |
|------|------|------|
| 構建守護 ×1 | 執行 | 唯一的重編譯者（防止多人同時改同一檔案） |
| 修復 ×N | 執行 | 只讀證據（不可自行推測行為，必須引用規則或測試結果） |
| 分類查找 | 審查 | 按規則判斷，不憑直覺。每個修復必引用規則手冊條目編號 |

### 自我驗證
- Q1：行為表面對齊但邏輯不同（偽陽性通過）
- Q2：反證 = 變更一個邊界輸入，觀察行為是否仍一致
- Q3：回滾 = 標記為「假性通過」，加入邊界測試後重驗

**Gate**：所有測試通過 + 邊界測試無假性通過 → 通過

## 共享文檔清單（規則比程式碼活得更久）

每次執行此 SOP 必產出並維護以下文檔：

| 文檔 | 內容 | 存放位置 |
|------|------|---------|
| 規則手冊 | 每條決策規則 + WHY + 邊界 | `docs/research/{task}_rules.md` |
| 依賴圖 | 工作順序 + 平行/串行標記 | 同上或 SVG |
| 差異清單 | 所有控制流變更點 | `docs/research/{task}_diff_checklist.md` |
| 原始程式碼 | 修改前的完整快照 | git ref (commit hash) |
| 陷阱 + 跳過列表 | 已知陷阱 + 刻意跳過的項目及原因 | 規則手冊附錄 |
| 分類帳本 | 每個 bug 的分類、根因、修復、驗證狀態 | `docs/research/{task}_bug_ledger.md` |

---

## 全域自我驗證迴圈

在 Step 6 完成後，執行最終自我驗證：

```
1. 回顧 Step 0 的三個問題 — 哪些最壞情境真的發生了？
2. 規則手冊中哪些規則從未被引用？（可能是多餘的，也可能是盲區）
3. Bug 帳本中最常見的根因類別 → 這代表規則手冊的哪個區域最弱？
4. 如果明天要對結果做一次完整重審，你會從哪裡開始？（這就是最脆弱的環節）
```

將答案寫入 `{task}_postmortem.md`，作為下次執行此 SOP 的輸入。
