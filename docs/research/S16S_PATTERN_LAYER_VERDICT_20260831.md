## 4. 驗收過程中抓到的兩件事

### 4.1 鑽石翻轉 = 真的 bug，護欄抓到

第一次跑印 `DIA TALLY P30=1 P61=0`，參考值是 `0 / 1`。

`S16S_DIAMOND_CLOSED_20260828.md` 第 151–156 行記載：8/28 指標印 P61，
且**離線把十槽鏈原樣移植回 Python 逐根模擬也是 P61**，兩邊一致。所以參考值是對的。

**原因**：鑽石用 M7 在**第一個樞紐**分頂／底（裁示 12），但程式讀 `v_DM7a[0]` 寫死 0。
杯柄編碼把這條鏈從 10 槽加寬到 12 槽，視窗起點 `v_d0 = v_DChain - 10` 現在是 **2**，
所以它讀的是鑽石開始**前兩個**的樞紐。已改為 `v_DM7a[v_d0]`。

全檔只有這一條帶偏移的鏈、只有這一個寫死的 0。P29 鏈沒有偏移，那裡的 `[0]` 正確。

**8/30 的 handoff 預言了這個失敗模式並把 `DIA TALLY` 放進驗收表。護欄運作正常。**

### 4.2 P68 1367 vs 1365 —— 程式碼對，註解錯

`s16s_groupA_scan.py` 給 **1,367**。參考值 `1365` 是 build 260870 寫的，
比 260872（`6b/6c` 移進 `if v_Push`）還早一版。參考值已更正。

**兩個看起來一樣的「對不上」，結論相反。分開查才看得出來。**

## 5. 驗證器盲點（第二次撞，這次修對地方）

`if cond then v_X = v_X + 1;` —— 指派在 `then` 之後、同一行，
行首錨定的 `ASSIGN` regex 看不到，把九個 P18/P57/P68 生命週期計數器
誤報成「只讀不寫，恆為初值 0」，**而 MC12 正在印它們的非零值**。

2026-08-28 撞過同一個盲點。當時選了便宜的做法：改 `.pla` 寫法，不改驗證器。
於是 8/30 另一台機器用同樣寫法，它又回來了。

**假 WARN 的代價不是吵，是讓真的漏賦值被當雜訊略過。**

已加 `POST_THEN` 規則與六個自測案例，其中三個是負向對照
（`then begin`／`then` 收尾／條件裡的比較）。
