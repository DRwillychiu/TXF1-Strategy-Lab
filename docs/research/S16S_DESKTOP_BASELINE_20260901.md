### 副作用，以及為什麼要有這一份文件

參考值是在完整資料上取的。**在 3% 的資料缺口下，一個真正 3% 的回歸會完全看不見。**

2026-09-01 能判定 Build 260911「零回歸」，純粹因為手上剛好有 2026-08-30
Build 260873 在**同一張桌機圖**上的輸出可以逐項比對。
下一次沒有那個對照組就判不了。

所以本檔把 260911 的桌機輸出**存成桌機基準**。
桌機以後的驗收對這一組，不對筆電的參考值。

## 3. ★ P17／P68 代號錯置

### 事實

| | 內容 |
|---|---|
| 指標裡標成 `P68` 的判定式 | `v_PvTyp[a] = 1 and v_PvPx[a] = v_PvPx[a + 2]` |
| 白話 | **兩個完全等高的樞紐高** |
| 圖鑑 **P17 雙頂** | 「**兩個完全等高的樞紐高**，同一價位被拒兩次」 |
| 圖鑑 **P68 雙頂四變體** | 「Bulkowski 依兩個頂是**尖是圓**，再細分成四種」 |

**指標裡的「P68」實際上是 P17。**

### 從哪裡開始錯的

Build 260870（2026-08-29）編碼樞紐型 A 組時，我把型態命名為「P68 雙頂」，
並註明「四變體不採 —— 尖 vs 圓本質上是曲率參數」。

**那個判定沒有錯**：四變體確實需要曲率門檻，確實不該編碼。
錯的是**它被套在 P68 這個代號上**，而 P68 指的就是四變體；
真正的基礎雙頂是 **P17**，當時躺在「未審查」清單裡沒有被碰。

### 波及範圍

| 何處 | 現況 |
|---|---|
| 圖表標籤 | 印 `P68 #n`，應為 `P17 #n` |
| `REV TALLY` ／ `P68 LIFE` | 欄位名稱是 P68 |
| 落地地圖 | P68 算「已畫」、P17 算「未審查」—— **兩個都反了** |
| 母體普查頁 ／ A 組頁 ／ 判決文件 | 全部稱它 P68 |
| 「13 種邏輯從未審查」 | 實際是 **12 種**，P17 已經畫在圖上了 |

### 數字沒有錯

**只有代號錯，判定式與所有計數都是對的。** 1,337（桌機）／1,367（筆電）
量的就是「兩個完全等高的樞紐高」，那是 P17 的母體。

### 待裁示

改名要動指標（標籤、計數器名、TALLY 欄位）、四份 HTML、落地地圖與三份文件。
**改名不改數字**，但會讓 `REV TALLY` 的欄位從 P68 變成 P17，
與 2026-08-30／08-31 已存檔的驗收表對不上欄位名。

兩個選項：

| | 做法 |
|---|---|
| **A** | **正名** —— 全部改成 P17，並在文件註明「2026-08-29 至 09-01 期間標為 P68」 |
| **B** | **不改，只註記** —— 保留 P68 這個標籤，在文件寫明它實際是 P17 的定義 |

建議 **A**。代號在這個專案裡是主鍵 —— 落地地圖、圖鑑、盤點表全都用它索引，
留著一個指向錯誤定義的主鍵，下一次有人查 P68 就會拿到不是四變體的東西。
