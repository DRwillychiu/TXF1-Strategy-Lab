# MC12 匯出格式與資料實測

> 2026-09-06 由實際檔案 `TXF1_1_分鐘.txt` 確認。2,087,650 列，106 MB。

## 格式

```
<Date>, <Time>, <Open>, <High>, <Low>, <Close>, <Volume>
2019/1/2,08:46:00.000,9760,9762,9745,9750,2997
```

| 項目 | 值 |
|---|---|
| 日期 | `2019/1/2` —— **月日不補零** |
| 時間 | `08:46:00.000` —— HH:MM:SS.mmm |
| 換行 | CRLF |
| 期間 | 2019-01-02 ~ **2026-08-22** |

## 戳記語意：收盤

日盤 08:45 開盤，第一根戳 **08:46**。

```
日盤   08:46 → 13:45   300 根
夜盤   15:01 → 05:00   840 根（跨日，00:00 戳記屬隔一曆日）
合計   唯一戳記 1140 = 300 + 840
```

**聚合規則直接推得出來**：連續 N 根取最後一根的戳記。
60M → `08:46-09:45` 戳 `09:45`，與 L2 標頭「day 09:45-13:45,
night 16:00-05:00」逐字相符。

## 資料品質

| 檢查 | 結果 |
|---|---|
| OHLC 不一致 | **0** |
| 零成交量 | **0** |

> **零成交量筆數為 0，代表無成交的分鐘直接省略，不是補成量 0 的 K 棒。**
> 實測：2026/6/1 夜盤跳過 19:23。
>
> 所以聚合器必須容忍缺漏，並記錄每根由幾根合成
> （`Bar.tick_count` + `QualityFlag`）。這是規劃書層 1 的 K 棒品質標記。

## ★ 結算日的日盤在 13:30 收

這是本次資料實測最重要的發現。

```
結算日     日盤 08:46 → 13:30   285 分鐘
一般日     日盤 08:46 → 13:45   300 分鐘
```

**92 個結算日全部如此，零例外。**

後果：60M 在結算日的末根戳 **1330**，是一根 45 分鐘的殘棒。
`quotes/session.py` 原本寫死 300 分鐘，在結算日是錯的，已修正。

## ★ 靜態結算規則漏標兩天

五份 `.pla` 都用 `DayOfWeek = 3 and DayOfMonth in [15,21]`。
五份規格表都把「第三個週三遇休市會標錯」列為 D-6。**現在量化了：**

| | 天數 |
|---|---|
| 資料反推的結算日 | **92** |
| 靜態規則標的 | 90 |
| 規則漏標 | **2** |
| 規則誤標 | **0** |

漏標的兩天：

```
2023-01-30（一）
2026-02-23（一）
```

**兩天都是農曆年後的週一——結算因假期遞延。**

反推方法：TXF 近月合約在結算日 13:30 停止交易，其餘交易日到 13:45。
「日盤末根戳記 = 1330」就是結算日。已做成 `tradecal/settlement.py`
的資料資產，超出 2019-01-02 ~ 2026-08-22 時退回靜態規則並可告警。

## 每日 K 棒數（依曆日，非交易日）

```
1140   Tue–Fri 完整      = 00:00-05:00(301) + 日盤(300) + 15:01-23:59(539)
 839   Monday            = 日盤(300) + 15:01-23:59(539)，前無夜盤尾段
 301   Saturday          = 只有 00:00-05:00
```

低於這些數字者為缺漏分鐘，屬常態。

## 效能

讀取 + 聚合 3 個月（69,195 列 → 1,160 根 60M）約 **11.6 秒**。
全檔 208 萬列外推約 **6 分鐘**。

反覆執行時應快取聚合結果，否則每次回測都要重讀 106 MB。
