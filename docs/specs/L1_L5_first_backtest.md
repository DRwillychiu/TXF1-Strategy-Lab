### ★ 已知結構性落差：本移植在收盤評估，不是 IOG 逐 tick

L1 是五支裡唯一 `IntrabarOrderGeneration = true`。原始碼把
**指標 / 週線 / 假日 / 進場 / P3 凍結 / 跳空分支**包在 `BarStatus(1) = 2` 內，
而 **P7 峰值追蹤 / P4 棘輪 / 出場下單**在守衛外逐 tick 執行。

`engine/context.py` 尚未實作，所以全部在收盤評估。後果：

```
P7 只看得到收盤峰值 -> posble_profit 偏低 -> stop_profit_price 偏低
-> TL_SP 觸發次數是**下限**，不是實際值
```

V3.0 把 SP 門檻從 500 降到 200 **正是因為 IOG 讓更低的門檻可行**。
用 200 跑收盤評估，既不是 V2.7 也不是 V3.2 的行為。

> **這不是參數問題，是結構問題。** 修法是實作 tick 生命週期。

而 anchor 本身也不可信：V3.2 明載
「Trade counts in the older documents are **NOT a valid baseline**.
TWO runs are required.」

### 診斷：分批出場幾乎不發生，所以跑單機制從未啟動

`BL_TP` 只有 10 筆。沒有分批就沒有 `CurrentContracts < MaxContracts`，
**Stage 2/3 的 MFE 三階追蹤永遠不執行**——而那正是 L5 賺錢的機制。

超過一半（138 筆）走 31 根的時間停損，代表**部位在到達目標前就被時間砍掉**。

### 已排除：日線定義

L5 的箱體建在日線上，所以日線的定義至關重要。實測三種：

| 日線定義 | L5 筆數 | L5 淨利 | L3 差 | L4 差 |
|---|---|---|---|---|
| **A 日盤 + 隨後夜盤**（現行） | 255 | −79,969 | **+3** | **+1** |
| B 前夜盤 + 日盤 | 247 | +1,462,591 | −19 | +2 |
| C 只有日盤 | 294 | −270,584 | — | — |

**B 讓 L5 好很多（淨 +1.46M，接近 MC 的 1.71M），但讓 L3 從 +3 變成 −19。**

三支對日線定義的偏好不一致。**保留 A**——它讓 L3/L4 維持在 +3/+1，
那是目前最好的對帳狀態。

> 這本身是個發現：**要嘛 MC 的各張圖用不同的 session 設定，
> 要嘛 L5 還有別的問題。** 需要 MC 的日線匯出才能定案。
