# 死設定與結構缺口 2026-09-06

> **緣起**：用戶要求「我在自己機器上跑的每個數字，你也要能驗證」。
> 建 `verify_claims.py` 時檢查 `FillPolicy` 的四個欄位，發現兩個從未被讀取。

## 找到什麼

```
policy.intrabar               2 次引用
policy.gap                    2 次引用
policy.allow_same_bar_exit    0 次   ← 死設定
policy.engine_stop_first      0 次   ← 死設定
```

**更糟的是 `allow_same_bar_exit` 出現在 policy 名稱裡（`sb=1`），
而那個名稱印在每一份報告上——報告一直在宣稱一個沒有作用的設定。**

## 而它掩蓋了一個結構缺口

```
我的 runner    進場填在 bar N 開盤 → 引擎停損檢查在填入之前
               → 新開的部位在同一根裡永遠不會被檢查
               → **同根進出場結構上不可能**

MC             L1 的 V2.9 取證明確記錄「12 筆同根死亡填在寬腿」
```

**MC 會，我不會。** 而我的 PF 在 L2 與 L4 都高於 MC——缺少同根停損正好造成這個方向的偏差。

## 接上之後立刻產生對帳證據

L2 全歷史 2×2，用**虧損出場的標籤向量**對 MC 的 `(22, 18, 4, 1)`：

| sb | ef | InitSL_D | InitSL_N | ENGINE | TSL_N | L1 距離 |
|---|---|---|---|---|---|---|
| **False** | **False** | **23** | **19** | **5** | **1** | **3** |
| True | False | 21 | 17 | 9 | 1 | 7 |
| False | True | 21 | 13 | 13 | 1 | 15 |
| True | True | 21 | 13 | 13 | 1 | 15 |
| **MC 標頭** | | 22 | 18 | 4 | 1 | 0 |

**兩者皆 `False` 最接近，每個標籤各差 +1。**

引擎停損在 MC 裡是罕見路徑（45 筆虧損出場中只有 4 筆），
`ef=True` 會讓它變成 13 筆——差距立刻拉開五倍。

> **這是逐筆對帳之外，第一個能判定成交假設的訊號。**
> 而它來自一個我原本以為只是死碼的欄位。

## 結論的兩面

**好的一面**：我原本的隱含行為（無同根出場、自訂出場優先）本來就是最接近的。
差別在於**以前是碰巧對，現在是量化確認的**。

**不好的一面**：`allow_same_bar_exit = False` 與 L1 的證據衝突。
L1 記錄了 12 筆同根死亡，代表 MC 在 L1 上**確實**會同根出場。

**移植 L1 時必須重跑這個 2×2。** 已寫進 `fill_mc12.py` 的註解。

## 防止再發生

```python
def test_no_dead_switches_in_fill_policy():
    """policy 的每個欄位都必須真的被讀取。"""
    for f in fields(FillPolicy):
        assert f"policy.{f.name}" in src, f"policy.{f.name} 是死設定"
```

`verify_claims.py` 也加了同樣的檢查，你跑的時候會看到四個 `✓`。

## 這一類缺陷的特徵

**沒有任何斷言會失敗。** 死設定不會崩潰、不會報錯、測試全過。
`sb=1` 印在報告上看起來很正常。

發現它的唯一途徑是**主動問「這個欄位真的被讀了嗎」**——
而那個問題是在建「讓用戶驗證我的說法」的工具時才浮出來的。

> 與 `spans_rollover` 標記錯誤同一類：**沒有斷言能發現「語意錯了」。**
