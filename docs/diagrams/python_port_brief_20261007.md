## 一、系統圖（由哪幾塊組成）

- **錄製系統**：全天錄製 6 個商品 → Python 的報價來源
- **Python 引擎（txfcore）**，依序：
  - 報價層：tick 組成 K 棒
  - 策略層：L1–L5
  - 風險層：Kill、連虧暫停、MDD 停用
  - 下單出口
- **下單大師**：
  - 用 API 收委託，委託名稱依下單大師公開規範
  - 送到券商
  - 內建 TG 通知
  - 內建部位核對，只提醒、不補單
- **券商**
- **MC**：Q4 期間照舊經下單大師下單
- **對帳**：Python 訊號與 MC 訊號逐筆比對，每天出一份報告
- **狀態與日誌**：部位、策略變數存檔，重啟後接續

## 二、架構圖（一頁，只放標題）

- 一般結構：
  - 層 0：基礎設施
  - 共用：指標、交易日曆、引擎
  - 1 報價 → 2 策略 → 3 風險 → 5 下單通知
  - 旁路：對帳
  - 組裝根：回測、即時
- 三顆插頭：
  - 報價插頭 ＝ 錄製系統轉接
  - 下單插頭 ＝ 下單大師 API 轉接
  - 時鐘
- 線條：
  - 實線 ＝ 平時（Q4）：MC 下單，Python 只出訊號、對帳
  - 橘色虛線 ＝ 接管（最快 2027/1）：Python 下單，MC 退場
- 標出已完成與空白：
  - 依 `LAYERS.md`：策略層只有 L2 完成；下單、通知、即時組裝都是空白
  - 五支的移植版本停在 9/6（L1 v3.2、L2 v5.4、L3 v15.1、L4 v14.7、L5 v19.9-R1），要更新到定案版

## 三、流程圖（每個判斷兩個出口）

1. tick 到達
   - 錄製系統斷線或延遲 → 停止新進場、TG 通知
2. K 棒完成？
   - 否 → IOG 策略（L1）在 K 棒內檢查停損；其他策略等 K 棒完成
3. 策略出訊號
4. 風險層放行？
   - 否 → 記錄並通知
5. 委託名稱轉成下單大師規範名稱
   - 對不到 → 拒送、TG 通知
6. 呼叫下單大師 API
   - 拒單或逾時 → 重試一次；仍失敗就停單、TG 通知
7. 成交回報？
   - 逾時 → 查詢部位
8. 更新部位
9. Python 部位、下單大師部位、券商部位三者一致？
   - 否 → 停止所有下單、TG 通知（現行規則）
10. 外部系統節點，各附「我們在這裡會發生什麼」：
    - 錄製系統斷線
    - 換月（近月轉遠月）
    - 結算日
    - 08:45、15:00 開盤跳空
    - 下單大師拒單
