## 2. 六層架構

用戶原始規劃三層（報價 / 訊號通知 / 策略決策），討論後補上三層：
**對帳層**（Claude 提出）、**風險管理層**、**回測層**（用戶提出）。

### 2.1 正確的切法是「線上跑的」與「旁邊驗的」

```
    +------------ 線上每天在跑 ------------+
    (1)報價層 -> (3)策略決策層 -> (5)風險管理層 -> (2)訊號通知層
                      |                |
    +-----------------+----------------+---------------+
    |  (6)回測層：換掉兩端，中間一個字都不能改           |
    |     報價來源 -> 歷史 K 棒                        |
    |     訂單去向 -> 記錄器                           |
    +--------------------+-----------------------------+
                         v
                   (4)對帳層  <-->  MC12 報告
```

### 2.2 鐵則

> ## 回測與即時，必須跑**同一份策略程式碼、同一份風險管理程式碼**。
> ## 只有「報價從哪來」和「訂單往哪去」不同。

**若回測與即時是兩份程式碼，對帳通過這件事不會傳遞到線上。**
那是量化系統最經典的死法：回測完美、實盤不一樣，而且永遠找不出差在哪。

### 2.3 建議的 package 佈局

**不開新 repo。** 理由：`scripts/taifex_calendar.py` 已在此，且它是 `.pla` 那 66 行陣列的**生成來源**，
搬走會立刻產生第二份真相；MC12 報告、`compare_mc12_reports.py`、`verify_*.py`、CLAUDE.md 16 條規則也都在這裡。

**但 `txfcore/` 必須與 `scripts/` 嚴格分開**——`scripts/` 是 40 幾支拋棄式研究腳本加一堆 `_temp_*.pkl`；
`txfcore/` 是要被信任的長期資產，必須有測試、有型別、有版本。


### 2.4 通知層為什麼排最後

**風險不對稱。** 訊號通知層是唯一一層**會讓人根據錯的訊號動用真錢**的東西。
在策略層被證明與 MC12 等價之前，把訊號推到手機上，等於把未驗證的系統接到下單手上。

## 3. ★ 檢測框架：四個判官

**用戶提問：「如果出現像 MC12 的進出場問題，我要如何做檢測？從哪邊模型做檢測？要如何排除我自己沒發現的問題？」**

### 3.1 先講殘酷的事實

把本 repo 近三個月**真實發生過的五個進出場事故**，逐一問「哪個機制會抓到它」：

| 事故 | 日期 | (1)逐筆對帳 | (2)不變量 | (3)獨立重算 | (4)事前登記 |
|---|---|---|---|---|---|
| L4 v18 二次進場**零觸發** | 08-24 | X | X | 部分 | **O** |
| V2.9 P3b **MaxList/MinList 取錯邊** | 07-22 | X | **O** | **O** | X |
| L2 v5.4 **定義錯位** | 08-25 | X | **O** | **O** | **O** |
| L3 基準線**自己從 360 變 361** | 08-25 | 部分 | X | X | X |
| **對帳工具本身**不合併分批出場 | 08-25 | X | **O** | **O** | X |

> ## **逐筆對帳，五個裡面抓到 0.5 個。**
> ## **其中三個事故，對帳當場印的是「通過」——因為兩邊確實一模一樣，只是一起錯。**

### 3.2 五個事故的共同點

**沒有一個是「策略邏輯想錯了」。五個全部是「觀測系統說謊了」。**

停損照設計走、標籤照定義貼、報告照格式匯出——每一層都在做它以為對的事，
而錯誤發生在**層與層之間的接縫**：

- 註解與程式碼的接縫（V2.9）
- 離線定義與下單時機的接縫（L2 v5.4）
- 報告列與實際部位的接縫（`read_trades`）
- 舊檔案與新檔案的接縫（L3 基準線）
- 設計意圖與觸發現實的接縫（L4 v18）

> **所以「排除自己沒發現的問題」不能靠更用力看，只能靠讓系統自己說。**
> **人不會發現接縫，因為接縫兩邊各自看起來都是對的。**

### 3.3 四個判官各自的職責

| 判官 | 抓什麼 | 抓不到什麼 | 現成資產 |
|---|---|---|---|
| **(1) 逐筆對帳** | Python 自己寫錯 | **兩邊共有的誤解** | `compare_mc12_reports.py` |
| **(2) 不變量檢查** | **兩邊一起錯**的東西 | 沒被寫成不變量的東西 | 無，要建 |
| **(3) 獨立重算** | 文件與程式碼不一致 | 三個模型一起錯 | V2.9 forensics 是先例 |
| **(4) 事前登記** | 你以為會發生、實際沒發生 | 你沒想到要登記的 | 執行卡制度已有 |

**(1) 證明的是「一致」，不是「正確」。**

**(3) 這個 repo 已經用過一次而且成功**：V2.9 那個 bug 是用
「100 萬根 K 棒重建 ATR45 / DailyATR、456 筆交易、凍結距離預測誤差 p90 = 1 點」抓出來的。

**(4) 的關鍵是登記「觸發次數」，不只登記績效。**
L4 v18 那次，如果事前登記了「預期觸發 N 次」，零觸發當場就是紅燈。

### 3.4 第五個機制：不可變匯出

**L3 基準線移動那個事故，四個判官全部抓不到**，因為舊檔案已經不存在。

> ## MC12 報告不得用同一個檔名重複匯出。檔名必須帶版本或時間戳。
> ## 建議再加 SHA-256，並把 hash 寫進對應的結果文件。

## 4. ★ L1 的 13 條不變量

### 4.1 從哪裡推導 —— **從註解，不從程式碼**

> **如果不變量是從程式碼推導的，那個測試永遠不會失敗**，它只是把程式碼換句話說一遍。
> **要抓到 bug，斷言必須來自「這支策略承諾保證什麼」，而那句承諾寫在註解裡。**

**L1 的 332 行註解，其實就是一份規格書。**

### 4.2 清單

| # | 註解原文的承諾 | 可執行斷言 |
|---|---|---|
| 1 | P3「computed once on the entry bar close and **locked**」 | `v_SL_Locked` 為真後，`v_Frozen_SL` 整筆交易期間不得改變 |
| 2 | P3「MaxList picks the **TIGHTEST**」 | `v_Frozen_SL` == `Entry - MinList(三個距離)` |
| 3 | **P3b「Distance = same as P3 frozen SL」** | **引擎停損距離 == 凍結停損距離** |
| 4 | P4「**uni-directional** ratchet」 | 持倉期間 `v_Trail_High[t] >= v_Trail_High[t-1]` |
| 5 | P7「an armed runner can **never** round-trip into a loss」 | `stopProfitPrice_L > 0` 蘊含 `stopProfitPrice_L > Entry_P` |
| 6 | P7「giveback from peak **capped at 55 pct**」 | 出場價 >= `Entry + peak * 0.45` |
| 7 | P5「**Iron Rule**: flat before the 05:00 close」 | 假日尾盤 `Time >= Holiday_Flat_Time` 絕不持倉 |
| 8 | P5「beyond the verified registry: **no entries, flatten all**」 | `Date > Registry_Valid_Until` 時不得有新進場 |
| 9 | P6「flat-time 12:30 before 13:30 settlement」 | 結算日 `Time >= Settlement_Flat_Time` 不得持倉 |
| 10 | P3b「active on the **ENTRY BAR itself**」 | 進場那一根，保護性停損已生效 |
| 11 | 單一部位策略 | `MarketPosition` 屬於 {0, 1} |
| 12 | V2.9.1「loss side and profit side **never share a label**」 | `TL_SL` 出場價 == 凍結停損；`TL_TP` 出場價 >= 進場價 |
| 13 | `AvgTrueRange(ATR_Length)[1] of Data2` 的那個 `[1]` | **決策時可計算性**：每個條件只能讀下單當下已存在的資料 |

**第 3 條就是 V2.9 那個 bug。** 註解白紙黑字寫著「距離相同」，程式碼取了相反的一邊，
**橫跨整個 V2.6+ 世代沒被發現**——因為沒有人把那句話變成會叫的東西。

**第 13 條就是 L2 v5.4 那個坑。** 拿掉 `[1]` 就是未來函數，回測會很漂亮，實盤會賠錢。

### 4.3 這 13 條不是為 Python 寫的

> **它們對 MC12 一樣成立。**
> **Python 版真正的價值，是它能在每一根 K 棒上檢查這 13 條，而 MC12 做不到。**

**不變量必須在執行時檢查，不是事後檢查**——回測與即時都要跑。

## 5. Phase 0：K 棒對帳（在任何策略對帳之前）

### 5.1 報價來源已解除阻塞

**用戶回覆（2026-09-02）：已有凱基 API `quotecom` 經驗，其他專案已做到毫秒級 tick 擷取。**

### 5.2 但冒出一個更隱蔽的風險

> ## MC12 的回測基準，是用 **MC12 自己的 K 棒**建立的。
> ## 凱基 tick 合成的 45M K 棒，**不保證**與 MC12 的 45M K 棒相同。

五個差異來源，每一個都足以讓對帳永遠不通過：

| 來源 | 為什麼會不同 |
|---|---|
| **45M 網格起點** | 日盤 08:45 開盤，網格是 08:45 / 09:30 / 10:15…？夜盤 15:00 怎麼接上去？ |
| **夜盤跨日的日期戳** | **L1 的 `Holiday_Tail` 語意完全建立在「00:00-05:00 的 K 棒戳記為隔天」上**。差一天，整個假日模組失效 |
| **換月接續** | TXF1 是連續近月合成，換月那天兩份資料怎麼接 |
| **集合競價 / 缺 tick** | 有沒有 K 棒、K 棒的 OHLC 是什麼 |
| **`of Data2` 對齊** | 「當下已完成的那一根日線」是哪一根 |

**如果 K 棒不同，逐筆對帳會一直紅燈，而分不清問題出在 K 棒還是引擎。**

**Phase 0 做法**：MC12 匯出 45M OHLC，凱基 tick 合成 45M OHLC，**逐根比 O/H/L/C 與時間戳**。

### 5.3 ⚠⚠ 本次討論的重大發現：**L1 是五支裡唯一 IOG = true 的**

```
L1_TrendLong           [IntrabarOrderGeneration = true]
L2_TrendShort          未宣告 -> 預設 false
L3_ConsolidationLong   未宣告 -> 預設 false
L4_ConsolidationShort  [IntrabarOrderGeneration = false]
L5_BreakoutLong        未宣告 -> 預設 false
```

**而 L1 的 P7 停利保護區塊沒有 `BarStatus(1) = 2` 護欄**（出場區第 32 行），
所以它**逐 tick 執行**，那裡的 `Close` 是**當下成交價**，不是 K 棒收盤價。
`stopProfitPoints_Long` 的註解也直接寫著「(V3.0: 500->200, **IOG**)」。

**後果：**

| | |
|---|---|
| **L1 需要 tick 級重放** | K 棒對帳對 L1 **不夠**，必須做到 tick 對帳 |
| **L2 / L3 / L4 / L5 只需 bar close 評估** | 大幅簡化，K 棒對帳就足夠 |
| **凱基毫秒級 tick 從「加分」變成「必要」** | 對 L1 而言 |

> ### 這改變了推進順序的建議：**L1 是五支裡最難的一支，不是最容易的。**
> ### 從 L3 或 L4 起步，可以用低一個等級的難度先把執行層與對帳層建起來。
> ### **此為建議，最終順序由用戶裁示。**

## 6. 風險管理層**沒有錨點可以對**

前面所有驗證方法都依賴「MC12 做過，我來複述」。**風險管理層沒有這個依靠。**

MC12 一次只跑一支策略、一個帳戶、固定口數。它從來沒回答過：

| 問題 | MC12 的答案 |
|---|---|
| 五支同時發訊號怎麼辦 | 沒有 |
| 總曝險上限 | 沒有 |
| 日內累計虧損達 X 就停止 | 沒有 |
| 斷線 / 報價延遲時該不該下單 | 沒有 |
| 券商回報的部位與系統認知不符 | 沒有 |

**必須改用另外三種方法驗證：**

1. **不變量**（總口數 <= 上限、單筆風險 <= 帳戶 X%、任何時刻部位可對帳）
2. **情境重放**（把五支的歷史訊號疊在同一條時間軸，數出歷史上有幾次同時觸發、最大同時曝險多少）
3. **故障注入**（斷線、延遲、部分成交、拒單、重複回報）

**第 2 項會直接回答懸置中的 B-2**——五支的 MDD 目前是各自獨立算的
（L1 80.9% / L3 106.3% / L4 47.0% / L5 77.6%），**疊起來是多少從來沒人算過**。

## 7. 關於「下單的絕對」

**用戶定義（2026-09-02）：「策略決策層面包含進出場下單的絕對以及訊號觸發成立」。**

理解為：**每根 K 棒（或 L1 的每個 tick）收盤，策略必須輸出一個唯一、無歧義、可完整重現的訂單意圖。**

寫成不變量：

> 給定同一根 K 棒與同一組狀態，策略輸出的（方向 / 單型 / 價格 / 口數 / 標籤）
> 必須**完全確定**，重跑一萬次都一樣。

**前提條件就是第 13 條不變量：每個條件只能讀取下單當下已經存在的資料。**

## 8. 分階段路線

| Phase | 內容 | 通過標準 |
|---|---|---|
| **0** | **K 棒對帳**（先做，不可跳過） | MC12 OHLC 與凱基合成 OHLC 逐根相同 |
| **1** | 執行層 + 指標層 + 行事曆層 | 13 條不變量全部有可執行斷言 |
| **2** | **第一支策略逐筆對帳**（建議 L3 或 L4，非 L1） | 彙總指標與逐筆欄位零差異 |
| **3** | 其餘四支（**L1 需 tick 級**） | 同上 |
| **4** | 風險管理層 | 無錨點，改用不變量 + 情境重放 + 故障注入 |
| **5** | 訊號通知層 | 冪等 + 心跳 |
| **6** | 組合決策層 | 卡在 B-2 兩個前提 |

### 8.1 一條硬規則

> ## Python 引擎在**逐筆重現五支現行版本**之前，
