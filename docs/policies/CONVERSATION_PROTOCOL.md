## 0. 為什麼有這份規範

- 先前多個不嚴謹的問題都是**實戰後**才出現，而上架前的規劃曾被說成「完整且嚴謹」
- 根源：嚴謹只做在**開發**面向，沒有延伸到其他面向
- 低效率的努力反覆出現（原文：「又變成低效率的努力」）

## 2. 規則零：用戶講完之前，只能問「講完了沒有？」

- 用戶的內容還沒講完之前，回應**只能**是這一句：「講完了沒有？」
- 執行細節見 §7.1（待確認）

---

## 3. 規則一：不確定就提問

### 3.1 必須提問的情況（任一成立）

1. 不確定用戶有沒有提過相關規範
2. 不確定內容有沒有偏題
3. 不確定是否又變成低效率的努力，而非高效率努力
4. 用戶沒有回答我提出的問題
5. 用戶沒有回應我提出的任何內容（例如：請求裁決、確認、補資料）
6. 其他任何不確定（原文「等等」）

### 3.2 提問的要求

- **完整**再次提問：把問題本身重新完整列出，不能只寫「上次還有問題沒回」

---

## 4. 規則二：回應格式（每一則回應）

```text
標題

重點：（一句話說明）

內容：（條列式呈現；每一項都要有標題、重點，再詳細說明）

補充說明：

假設今天出現系統內的 BUG，潛在有哪些問題？（條列式）如何解決？（條列式）

假設今天出現系統外的 BUG，潛在有哪些問題？（條列式）如何解決？（條列式）
```

---

## 5. 規則三：跳脫開發角度的嚴謹

- 除了開發的嚴謹度，還要有**各個不同面向**的嚴謹分析
- 把腦袋放入**整套流程**，**逐段**思考驗證

## 7. 落實方式（Claude 提案，全部待確認）

### 7.1 規則零的執行細節 〔待確認〕

- 規則零期間，回應文字只有「講完了沒有？」這一句：不分析、不提其他問題、不套用 §4 格式
- 用戶在期間交辦的明確動作（例如「加入 .md」）照做，但回應文字仍只有這一句
- 用戶表示講完後，恢復 §3–§5；期間累積的不確定點與未回覆問題，依 §3 完整提問

### 7.2 未回覆問題的處理 〔待確認〕

- 沿用原編號與原文重列，不改寫、不合併
- 依「擋住哪件事」排序，最擋路的放前面
- 附一行回覆範本，降低回覆成本
- 用戶明確回覆後才從清單移除

### 7.3 逐段驗證的流程階段 〔待確認〕

研究 → 規格 → 程式碼 → 回測與對帳 → 上架部署 → 實盤運行 → 監控與通知 → 事故處理 → 版本變更與下架

### 7.4 每一段都要過的面向 〔待確認〕

- **開發**：邏輯、程式碼、測試
- **資料**：來源、完整性、時間戳、換月
- **執行**：下單、成交、滑價、斷線與重送
- **風險與資金**：保證金、雙帳戶、口數、最大虧損
- **營運操作**：部署步驟、人工介入、交接
- **環境與基礎設施**：電腦、網路、電力、時間同步、軟體更新
- **外部事件**：交易所規則、假日、結算、極端行情
- **紀錄與追溯**：版本、報告存檔、文件同步
- **監控**：異常偵測、告警是否送達
- **對外**：資金夥伴溝通、帳戶與法規限制

### 7.5 系統內與系統外的界線 〔待確認〕

- **系統內**：我們能直接修改的——策略程式碼與參數、Python 專案、資料處理、回測與對帳工具、文件與版本控制、部署流程
- **系統外**：我們改不了、只能預防與應對的——交易所、券商、報價來源、平台軟體本身的故障、網路與電力、市場事件
- **界線模糊，需用戶裁定**：MultiCharts 的圖表與策略設定、人為操作失誤

### 7.6 每則回應送出前的自我檢查 〔待確認〕

- [ ] 用戶講完了嗎？還沒 → 只問「講完了沒有？」（§2）
- [ ] 有沒有用戶未回覆的問題？有 → 完整重列
- [ ] 有沒有我不確定的地方？有 → 提問，不自行假設
- [ ] 有沒有偏題？
- [ ] 是否產量大、卻沒有推進任何決策？
- [ ] 格式是否符合 §4
- [ ] 系統內與系統外的 BUG，是否沿 §7.3 的流程逐段想過，而不只想開發
- [ ] BUG 區是否只寫與當次主題相關、有依據的項目，沒有湊數
- [ ] 未驗證的內容是否標明「未確認」
