**資料來源**：4 份 MC12 真實回測 xlsx
**結論**：**回滾 v14.5 → v14.4 default**，A 是 redundant、B 過度激進

## 二、為什麼 A 完全無效（被既有邏輯吃掉）

### A 的條件
```powerlanguage
v_Strong_Long_Block = Strong_Long_Filter_On and
                      (Fast_MA - Slow_MA) / Slow_MA * 100 >= 1.0
```

### 但 L4 既有 v_Macro_Block 條件（在進場 chain 中早就存在）
```powerlanguage
if ((v_Daily_FastMA >= v_Daily_FastMA[1]) and
    (v_Daily_SlowMA >= v_Daily_SlowMA[1]))
   or (v_Daily_FastMA > v_Daily_SlowMA) then
    v_Macro_Block = true;
```

### 邏輯關係（致命）

```
v_Macro_Block 觸發條件:  Fast > Slow  (or 兩 MA 都上升)
v_Strong_Long_Block 觸發: Fast - Slow > 1%

數學關係:
  Fast - Slow > 1%  →  Fast > Slow  (TRUE)
  
即：v_Strong_Long_Block 為 TRUE 的所有情況, v_Macro_Block 必為 TRUE
→ v_Strong_Long_Block 是 v_Macro_Block 的「子集」
→ 加它毫無作用，因為 Macro_Block 已經先擋了
```

### 證明：A only 樣本 = baseline 81 筆完全相同

**81 = 81** = A 沒過濾掉任何進場 = **redundant filter**

## 三、為什麼 B 反而更糟

### B 的設計
```powerlanguage
if Close > Locked_Top + Current_ATR * 0.5 then
    BuyToCover ("CS_FastBreakExit") next bar at Market;
```

### 出場標籤分布揭露真相

| 標籤 | v14.4 | B only | 差異 |
|------|-------|--------|------|
| CS_BreakExit | 20 筆 / -378K | **5 筆** / -98K | 多數轉到 FastBreakExit |
| **CS_FastBreakExit** | 0 | **27 筆** / **-437K** | 新增大量虧損 |
| 合計 (BE + FBE) | 20 / -378K | 32 / **-535K** | **更糟** |
| CS_SL | 26 / +500K | 20 / +618K | 樣本變少但單筆更賺 |

### 失敗原因解剖

**B 設計過度激進**：
1. 0.5 ATR Buffer 太小（≈ 30-50 點）
2. 盤整中正常波動就能觸發
3. **大量「假信號」被當成真突破砍倉**
4. 原本能透過 Trail 鎖利的部位被提早砍掉

**數學驗證**：
- 多 12 筆 (20→32) 進入 BreakExit 系列
- 多虧 -157K (-378K → -535K)
- 換算：**B 設計每筆多虧 ~13K**

**樣本反而變多** (81→85)：
- B 提早出場 → Cooldown 結束更早 → 下一筆進場更快
- 多進的 4 筆 = 多承擔風險

### CS_SL 的微小補償

CS_SL 樣本 26→20 但 +500K→+618K：
- 「能撐到 SL 觸發的」部位品質更高
- 但**整體仍是淨虧**（虧損的 BreakExit 系列多於賺的 SL）

## 五、最痛的真相

我的 v14.5 設計**重蹈 RangeForceExit 失敗的覆轍**：

| 教訓 | 對 v14.5 是否再犯 |
|------|----------------|
| 設計超前實證 | ✅ **再犯** |
| 沒檢查與既有邏輯的重複性 | ✅ **再犯**（A 被 Macro_Block 吃掉）|
| 過濾門檻沒實證決定 | ✅ **再犯**（B 0.5 ATR 太小）|
| 預設 ON 風險高 | ✅ **再犯**（A+B 都 default true）|

### 應該怎麼做

#### 設計 A 前該做的事
```
Step 1: grep L4 既有 entry conditions
Step 2: 列出所有「擋多頭結構」的現有 filter
Step 3: 判斷 A 是否與既有 redundant
Step 4: 若 redundant → 不做 A，或者把 A 設計成「補既有不足」
```

**我跳過 Step 1-3 直接設計 A** → 結果 100% redundant。

#### 設計 B 前該做的事
```
Step 1: 統計 v14.4 BreakExit 觸發前 N 根 K 的價格分布
Step 2: 找出「真突破」的特徵（持續時間、buffer 大小）
Step 3: 設計 buffer 大於「假信號」、小於「真信號」
Step 4: MC 驗證新 buffer 的觸發次數
```

**我憑感覺選 0.5 ATR** → 結果太小、觸發過多假信號。

## 六、回滾建議與下一步

### 立刻動作（必做）

**方案 A：完全回滾到 v14.4 default**
```
改 .pla:
  Strong_Long_Filter_On(true)  → Strong_Long_Filter_On(false)
  Fast_BreakExit_On(true)       → Fast_BreakExit_On(false)
  
但保留 input + 邏輯（供未來研究）
```

**方案 B：完全刪除 A，重新設計 B**
- 砍 A 邏輯（永遠 redundant）
- B 改 buffer 為 1.5 ATR 或 2.0 ATR
- 重跑驗證

我建議：**方案 A**（保守，先解除虧損風險）。
B 的重新設計留到下次。

### 後續研究方向（暫不上線）

#### A 改進方向
- 不要用 `Daily MA gap%`（與 Macro_Block 重複）
- 改用 `Daily ATR(20) 變化趨勢`（補既有不足的維度）
- 或 `Daily 連續上漲根數`

#### B 改進方向
- Buffer 從 0.5 ATR 提升到 1.5-2.0 ATR
- 加 confirm 條件：連續 2 根 15M Close > Threshold
- 加 time window：開盤後 N 小時內不觸發
- **必須先做 MFE/MAE 統計**再決定 buffer

## 七、教訓記憶

**寫入專案知識庫的 13 號教訓**：

> **任何過濾類 input 在設計前，必須 grep 既有所有 filter conditions，判斷是否 redundant。若新 filter 是既有的「子集」，加它毫無作用。**

對應到 issue：
- L4 v14.5 Strong_Long_Filter_On 是 v_Macro_Block 的子集
- S2 v0.4 VolFilter_On 在 Volume=0 時永遠 false
- 上次 RangeForceExit 在夜盤無上界永遠觸發

**統一原則**：**新 filter 必須做「歷史通過率」與「重疊度」雙重驗證**才能 default ON。
