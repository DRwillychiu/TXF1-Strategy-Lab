## 五、假日模組總體檢（鐵律落地）

### 5.1 日期驗證方法論（回答「精準度 100%?」）

**驗證層級（由高到低）：**

| 層級 | 來源 | 角色 |
|:---:|------|------|
| 1 | **期交所官方「期貨集中交易市場行事曆」PDF**（taifex.com.tw/file/taifex/CHINESE/4/2026Calendar.pdf） | **唯一準據** — 市場休市與政府放假不同（春節封關提早數日） |
| 2 | 期貨商行事曆頁（康和等） | 交叉檢核 |
| 3 | 人事行政總處系新聞/行事曆站 | Sanity check |
| 4 | **本策略自身回測交易明細時間戳** | 實證驗證（夜盤是否存在、成交是否真在假期前） |

本次 2026 下半年所有日期已完成 1+2+3 三源一致比對，並用第 4 層實證驗證了模組行為。

**「100%」的三個誠實邊界（無法靠任何流程消除）：**
1. 期交所 PDF 自註「本表僅供參考，實際最後交易日仍以各契約交易規則為準」
2. **颱風/天災臨時停市無法預先寫入** → 靠 Manual_Kill_Switch + 人工程序
3. 政府臨時調整放假（罕見）→ 靠季度複查捕捉

因此精準度的正確問法不是「一次查對」而是「**程序化**」：寫入前對官方 PDF 逐筆核對 → 每季初複查未來一季 → **每個連假前最後一週人工再確認**（已寫入 SOP）。

### 5.4 設計漏洞解剖（為什麼日期對了也擋不住）

現行邏輯：`if Date = Holiday_List[idx] and Time >= 1330 then 平倉`

- **漏洞 A（午夜尾段）**：前夕夜盤 15:00 開盤、跨午夜跑到次日凌晨 05:00。午夜後的 K 棒日期戳記變成「假日當天」≠ 陣列日期 → 00:00-05:00 完全無保護。實證 #2（03:45 進場）、#4（03:00 進場）都從這個洞鑽進去。
- **漏洞 B（無進場封鎖）**：模組只平倉、不擋新進場。實證：2020-09-30 22:30 進場 → 23:15 被踢、2023-10-06 22:30 進場 → 23:15 被踢——進去又被踢出，白繳滑價，且若發生在午夜後就變成漏洞 A。
- **確認有效的部分**：平倉成交全部落在前夕夜盤 15:00 開盤（24 筆 TL_Holiday 時間戳全數驗證），物理上確實在假期前出場 ✓。

### 5.5 修正設計：假日模組 v2（雙陣列 + 進場封鎖）

```powerlanguage
Inputs:  Holiday_Exit_Time(1230);   { 從 1330 提前到 1230 → 日盤 12:45 即出場 }

Arrays:  Holiday_Eve[60](0),        { 最後交易日 }
         Holiday_First[60](0);      { 首個休市日（= 前夕夜盤午夜後的日期戳） }

Vars:    v_Holiday_Mode(False), hidx(0);

{ === 偵測：前夕 12:30 後 或 假日當天凌晨 0500 前 === }
v_Holiday_Mode = False;
for hidx = 1 to 60 begin
    if (Date = Holiday_Eve[hidx]   and Time >= Holiday_Exit_Time) or
       (Date = Holiday_First[hidx] and Time <= 0500) then
        v_Holiday_Mode = True;
end;

{ === 平倉 === }
if v_Holiday_Mode and MarketPosition > 0 then
    Sell ("TL_Holiday") next bar at Market;

{ === 進場封鎖：原進場條件追加 and v_Holiday_Mode = False === }
```

涵蓋效果：前夕日盤 12:45 出場（不依賴夜盤存在）→ 前夕夜盤全程封鎖進場 → 午夜尾段（日期戳 = Holiday_First）繼續封鎖到 05:00 收盤。**鐵律完整落地。**
